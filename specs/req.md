# kb-agent 产品说明

- 一个属于我自己的 private 的 AI 知识库智能体
- 一个公网可以调用的 agent（以工具/能力形式被调用方 Agent 使用；不是替调用方完成全部业务推理的通用业务中台）

## 调用者

- IDE，如 Cursor IDE / Cursor Agent 中的项目
- 其他应用，如我自己开发的 HCP Engagement Assistant（https://hcp.agent-mate.ai）
- 第三方工具如 ChatBox（chatboxai.app）

上述调用方均须**自带大模型**（或由宿主应用接入 LLM），用于调用方一侧的意图理解、业务逻辑与知识消费。

## 功能

- 管理我在不同项目中与 AI 协作获得的知识
- 接入 Qwen LLM，**仅用于智能体内部的知识管理**（归类、整理、摘要提案、去重辅助等）
- 调用者可要求按需从外部知识源查找新材料，**确认后**整理归入知识库
- 调用者可按输入从知识库检索已有知识（返回可引用片段 / 结构化命中）
- 调用者可要求归纳整理知识体系（例如分类、标签、项目归属）

## 大模型与职责边界

### 调用方 LLM 负责

- 理解业务意图与任务目标
- 决定是否需要外部补给、如何解读检索结果
- 按调用方业务逻辑筛选、组合知识
- 使用知识产生业务洞察、策略、文案等下游产物
- 向用户解释结论（kb-agent 不替代调用方产品话术）

### kb-agent（及内部 Qwen）负责

- 知识库内检索、列表、体系整理
- 外部知识源的受控检索与正文拉取（补给管道）
- 入库提案（分类建议、摘要、查重）与确认后的持久化、分块、向量化
- 不将外部合成「成品答案」不经原文直接写入知识库

### 越界请求的应对

当调用者（或其上的模型）要求 kb-agent 完成**超出知识管理 / 知识补给**的工作时，kb-agent **拒绝代劳业务推理**，并按下列方式响应：

| 请求类型 | 示例 | 应对 |
| --- | --- | --- |
| 业务洞察 / 策略 | 「根据我们 HCP 本周数据，上网查竞品并给出投放策略。」 | **拒绝**生成投放策略或业务结论。可拆分协助：在权限与工具范围内做「竞品相关公开资料」的外部候选检索 → 返回候选与引用；明确说明策略须由调用方 LLM / 应用基于业务数据自行生成。不接受「把业务数据交给 kb-agent 并直接出策略」作为成功路径。 |
| 开放式调研结论 | 「帮我研究完直接告诉我该怎么做」 | 只提供检索片段 / 外部候选与来源；不给出最终业务决策。 |
| 静默全量入库 | 「网上相关的都自动进库」 | 拒绝。外部材料必须经提案，且需确认后才入库。 |
| 伪造库内知识 | 库中无依据却要求「就当知识库说过」 | 明确不足；可建议外部补给或入库提案，禁止捏造引用。 |

原则：**kb-agent 可以帮「找到并管好知识」，不可以替调用方「做完生意」。** 越界时返回稳定错误码或明确拒绝话术（工具结果 / API），便于调用方模型改走本侧推理。

## 获取新知识（产品要求）

- 优先使用知识库已有内容；不足时再启用外部补给
- 支持：调用方粘贴 / 单文件上传、**批量文档上传**、指定 URL 拉取、经源路由的外部搜索候选
- 外部搜索结果以**候选列表**形式返回（标题、URL、摘要、来源类型、质量相关信号）；不自动落库
- 选用或上传后进入「提案 → 确认 → 入库」；确认前不写向量、不建正式条目
- 「最优外部源」定义为：在预算与策略下的**自适应路由 + 证据优选**，而非固定单一搜索引擎

### 批量文档导入（有确认）

- 使用者可通过 API / MCP（或后续管理/工具面）**一次上传多份文档**，系统为每份可解析文档生成入库**提案**（抽取正文、摘要、分类建议、查重），组成一个导入批次。
- **禁止**「上传后静默全部进库」。必须经确认：支持**逐条确认**或对批次执行**一键确认全部有效提案**（显式操作，等同批量 confirm，不是跳过确认）。
- 支持格式（基线）：Markdown（`.md`）、纯文本（`.txt`）、PDF（可抽取文本者）；单文件与批次总大小、文件个数设上限。无法抽取正文的文件标记失败，不阻塞同批其他文件。
- 可选：上传时附带默认 `project` / 标签，写入各条提案元数据（仍可在确认前改）。
- 与越界规则一致：拒绝「网上相关的都自动进库」类无确认批量；批量上传必须走提案确认态。

## 多用户与鉴权（产品要求）

### 两套身份

| 身份 | 入口 | 凭证 | 职责 |
| --- | --- | --- | --- |
| **管理员** | Admin Web App（如 `/admin`） | 用户名或邮箱 + 密码（会话） | 邀请新管理员、登录、重设密码；签发 / 修改 / 吊销**使用者** API Key |
| **使用者** | MCP / App / REST 等任意调用方 | **一把** API Key | 使用自己的**全局唯一**知识库；不按调用方拆 Key |

- kb-agent 对每个使用者是**全局唯一知识库**；同一把 Key 可用于 ChatBox MCP、Cursor MCP、HCP App 等，无需按调用方区分。
- **一人一把有效 API Key**；签发时管理员填写**使用者姓名**。
- 使用者不能登录 Admin Web；管理员管理 Key 不依赖使用者自助注册。

### 管理员 Web（邀请制 R2 + Resend）

- 登录、重设密码；邮件（验证/邀请/重置）经 **Resend** 发送。
- **邀请制（R2）**：仅**已登录管理员**可邀请新管理员（输入邮箱 → Resend 发邀请链接 → 对方设置**英文姓名**与密码后成为管理员；顶栏显示 `Hello, {姓名}`）。**关闭**开放自助注册。
- **初始化默认管理员**：Web / Admin 在库中尚无管理员时，自动创建默认账号 **用户名 `admin` / 密码 `admin` / 邮箱 `me@ethanhuang.com`**（`BOOTSTRAP_ADMIN_EMAIL` 可覆盖；`must_change_password=true`）。**仅该种子默认口令路径**须在登录后先改密，方可使用邀请、签发 Key 等管理能力。经**邀请设密**或**忘记密码重置**自选密码的管理员不走强制改密。之后新管理员只走邀请。
- 管理台能力：
  - **管理员**：列表；邀请；删除（不可删自己；不可删光最后一名有效管理员）
  - **使用者 Key**：列表（仅有效 Key）；签发（**英文姓名**，明文单行可复制）；**查看**（姓名 + 完整 Key 可复制，密文存库见 ADR-007）；确认后吊销（列表移除该行，知识保留）；重签（同一使用者，知识库不断）。不提供改姓名。
- 登录页：开放注册已关闭；「联系管理员」悬停/聚焦展示微信二维码；密码框支持显示/隐藏。

### 知识 API 鉴权

- 一律 `Authorization: Bearer <api_key>`（MCP 与 REST 相同）。
- 身份以 Key 解析出的 `user_id` 为准；请求体中的用户标识不可覆盖。
- 各使用者数据强制隔离；默认无跨用户共享。

## 架构和技术要求

- 部署在香港 VPS 上；公网域名 **`kb.agent-mate.ai`**（HTTPS）
- 后台是 RAG 服务
- 知识存储放在 VPS 服务器上（本地目录或数据库）
- 对 Cursor / ChatBox 等：以 **MCP** 为一等接入（Cursor：Streamable HTTP **`/mcp`**；ChatBox：遗留 SSE **`/sse`**；设计见 `specs/mcp-design.md`）；对 HCP 等：提供结构化 **REST**（与 MCP 工具共用领域层）
- 可选提供 OpenAI 兼容门面，但仅作为「调用同一套知识工具」的薄封装，**不**扩展为无边界业务 Agent
- 提供 Admin Web App（同域不同路径即可，如 `https://kb.agent-mate.ai/admin`）

## 未来的扩展性

- 多用户以「管理员签发 Key + `user_id` 隔离」为基线；不引入按调用方多 Key、OAuth 使用者门户，除非需求变更。
- 当前与目标存储：知识原文、元数据与向量均落在 VPS（本地目录 + 数据库/向量库）。不采用 GitHub Gist 作为知识存储。若未来因磁盘压力外置大附件或原文，仅考虑 S3 兼容对象存储等方案；原文访问经存储抽象，避免业务逻辑直绑本地路径。不把 Gist 列入存储路线图。
